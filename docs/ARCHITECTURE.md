# アーキテクチャ

## 設計方針

このボットが守るべき性質は 1 つ。**毎朝必ず何かが届くこと。**
外部サービスは落ちるし HTML 構造は変わる。だから全体を「劣化はするが停止はしない」形にしてある。

| 壊れたもの | 起きること |
| --- | --- |
| GitHub Trending の HTML 構造 | そのソースだけスキップ、他ソースで配信 |
| Hugging Face API が 5xx | 3 回リトライ後スキップ |
| ネットワーク全滅 | 同梱の seed カタログだけで配信 |
| Anthropic API が落ちた / 拒否 | 抽出要約にフォールバック |
| Claude が一部の項目しか返さない | 欠けた分だけ抽出要約で補完 |
| 状態ファイルが壊れた | 空から作り直して続行（重複配信のリスクだけ負う） |
| LINE への push が失敗 | 状態を更新しない → 翌日リトライで取りこぼさない |

逆に、**黙って 0 件になる**のは許さない。GitHub Trending から 1 件も取れなかったときは
例外を投げてログに残す（パーサが壊れたサインなので、静かに成功されると気付けない）。

## レイヤ

```
cli.py           引数解析・設定の上書き・終了コード
  └─ pipeline.py  取得 → 採点 → 要約 → 配信のオーケストレーション
       ├─ sources/    外部からの取得 (github_trending / huggingface / note / seed)
       ├─ ranking.py  採点・重複排除・選抜
       ├─ summarize.py 日本語要約 (Claude / 抽出)
       ├─ render.py   Flex Message / テキスト / Markdown
       ├─ delivery/   LINE / コンソール
       └─ store.py    既配信の記録
```

依存は上から下への一方向のみ。`models.py` だけが全層から参照される。
`http.py` は標準ライブラリのみの薄い HTTP ラッパ。

### なぜランタイム依存ゼロなのか

必要なのは HTTP を数本叩くことだけで、`requests` も `line-bot-sdk` も要らない。
依存が無いぶん GitHub Actions のセットアップが速く、供給網の心配も減る。
`anthropic` SDK だけは optional extra (`[llm]`) で、遅延 import している。

## データフロー

```
DigestItem      ソースが返す生の候補（タイトル・URL・説明・指標）
    ↓ ranking
ScoredItem      スコアと「選ばれた理由」を付けたもの
    ↓ summarize
Highlight       日本語の見出し・本文・なぜ重要か（item_id で紐付け）
    ↓
Digest          1 回の配信単位（generated_at + items + highlights）
    ↓ render
LINE メッセージ / テキスト / Markdown
```

すべて frozen dataclass。段の間で状態を書き換えないので、途中の任意の段を
単体でテストできる（実際 `render` と `ranking` のテストは HTTP を一切踏まない）。

## 判断の記録

### 採点を加重和にした

学習ベースのランキングにする手もあるが、教師データが無い個人用ボットで
やることではない。加重和なら **なぜその項目が選ばれたかを 1 行で説明できる**。
`ScoredItem.reasons` に理由を持たせ、`--out` の Markdown に残しているのはそのため。
出力に不満が出たら、つまみ（`W_MOMENTUM` など 3 つの重みと `VEILE_INTERESTS`）を回す。

### 対数正規化

スター数は桁が大きく違う（30 と 30,000）。線形に扱うと巨大リポジトリが常に勝ち、
「今日伸びているもの」という趣旨から外れる。`log1p(x)/log1p(基準値)` で圧縮している。

### 重複排除はスコア順の上位だけに効かせる

全件に対して畳んでから切るより、**切ってから畳む** ほうが要約に回る件数が減り、
LLM コストが下がる。下位候補が畳まれ損ねても配信結果は変わらない。

### 状態は JSON 1 ファイル

1 日 10 件 × 21 日で数百エントリ。DB を持ち込む規模ではない。
書き込みは一時ファイル + `replace` の atomic 更新で、途中で落ちても壊れたファイルを残さない。

### LINE SDK を使わない

使うのは push エンドポイント 1 本だけ。SDK を挟むと再試行の挙動や
`X-Line-Retry-Key`（24 時間の重複排除キー）の制御が入れにくい。

### プロンプトキャッシュ

システムプロンプトは固定、候補 JSON は末尾。プレフィックスが安定するので
`cache_control` が効く。逆に言うと、**システムプロンプトに日付や件数を入れてはいけない**
（入れた瞬間にキャッシュが毎回無効化される）。

## 制約・既知の弱点

- **GitHub Trending は非公式**。ページ構造が変わればパーサが壊れる。壊れたときは
  例外 → ログ警告 → 他ソースで継続、という形で気付けるようにしてある。
  修正は `github_trending.py` の正規表現 4 本だけで済む。
- **seed カタログは一次情報ではない**。人が読んだまとめを写したもので、内容は未検証。
  配信時に必ず「※ 未検証の伝聞情報」を表示し、Claude にも断定を避けるよう指示している。
- **Flex Message は 50KB / カルーセル 12 バブル**。`render.py` が上限を超えないよう
  末尾から落とす。落とすのは常に低スコア側。
- **状態は 1 マシン前提**。複数環境から同時に走らせると重複配信が起きうる。
  Actions では `concurrency` グループで直列化している。

## 拡張するとき

新しいソースを足す場合:

1. `sources/` に `Source` を実装したクラスを追加（`fetch()` が `DigestItem` を返す）
2. `sources/__init__.py` の `registry` に登録
3. `config.py` の `source_weights` に重みを追加
4. パース関数を純粋関数に切り出し、保存した実データでテストを書く

配信先を足す場合は `delivery/` に `Deliverer` を実装する（Slack や Discord も同じ形で入る）。
